# 第一部分：最终产品定位

## 1. 核心定义

Pullet Studio 的最终定位为：

**面向个人及团队的 AI 影视创作工作空间。**

主要支持：

- 中国神话与知识类长视频。
- AI 短剧。
- AI 广告片。
- AI 电影及短片。
- 其他以图片、视频和音频为核心的创作。

我们不再将剧本管理、自动分镜、制作单元和 Shot 卡片作为强制主流程。

主要创作流程确定为：

**项目 → 无限画布 → 素材和提示词 → 工作流 → 生成 → 候选 → 资产复用 → 导出。**

用户允许以任意顺序准备创作素材。

例如：

- 先创建角色。
- 先上传场景。
- 先导入参考视频。
- 先填写提示词。
- 先生成角色设定图。
- 直接使用已有图片生成视频。

不应强制用户遵守某条固定流水线。

## 2. DX OS 是产品体验的第一标杆

我们已经分析了 DX OS 的实际运行环境与应用结构。

确认用户最喜欢的并不是它的天气、桌面小组件或应用市场，而是：

1. 产品有统一的视觉语言。
2. 功能组织清晰。
3. 像一个完整的创作工作空间。
4. 工具相互独立但共享资源。
5. 素材与结果始终可见、可复用。
6. 不要求用户理解大量技术概念就能开始工作。
7. 高级能力可以深入配置，但普通操作保持简单。

**请学习 DX OS 的产品设计质量和交互逻辑，而不是复刻整个 DX OS 操作系统。**

同时参考：

- hero8152/Infinite-Canvas：无限画布操作与生成面板。
- ddcat-ai/open-ai-canvas：影视语义资产和多媒体生产。
- basketikun/infinite-canvas：画布工程与节点交互。
- jtydhr88/ComfyArt：ComfyUI 工作流及生成体验。

这些只是辅助参考，不能变成同时开发多个软件的任务。

# 第二部分：正式技术架构冻结

## 3. 第一阶段不开发桌面客户端

这是最新确定的技术决策。

**Pullet Studio 第一阶段仅包含 Web 与 Server。**

技术结构：

```text
Pullet Studio
│
├── Web
│   ├── React + TypeScript
│   ├── React Flow
│   ├── 项目与多画布
│   ├── 资产库
│   ├── 提示词库
│   ├── 工作流中心
│   ├── 任务与结果
│   └── 管理设置
│
└── Server
    ├── NestJS API
    ├── 认证与 RBAC
    ├── 项目及资产服务
    ├── Board / Revision
    ├── Workflow Profile
    ├── Generation Service
    ├── Generation Worker
    ├── SQLite
    └── Storage
          │
          ├── 本地 SSD / NAS
          └── 多台 ComfyUI 实例
```

不创建 Electron 应用。

不创建 `apps/desktop`。

不开发应用安装市场、窗口沙箱、多应用运行时、桌面更新器或完整 Agent OS。

## 4. Web 版仍然必须具备桌面创作软件的体验

技术上是网站，不意味着视觉上应该像传统业务管理后台。

希望达到：

- DX OS 式整洁工作空间。
- 大面积自由创作画布。
- 清晰的工具入口。
- 灵活收起的资源面板。
- 轻量悬浮生成面板。
- 图片和视频内容优先。
- 适合长时间使用的深浅双主题。
- 完整键盘与鼠标交互。

但不需要模拟 Windows 的桌面系统、任务栏或任意窗口管理器。

## 5. 保留现有后端技术栈

继续使用：

- NestJS。
- Drizzle。
- SQLite。
- React。
- React Flow。
- 现有共享 Contracts。
- 现有 Media / Storage。
- 现有 Generation Service / Worker。
- 现有 Workspace / Project RBAC。

不能为了参考 DX OS 把后端切换为 Express，或者重新开发第二套数据库、任务队列与资产存储。

# 第三部分：信息架构与用户入口

## 6. Workspace 与 Project

继续保留底层 Workspace 和 Project 两个概念。

职责：

**Workspace**

- 团队身份。
- 成员管理。
- 共享计算资源。
- ComfyUI 实例。
- 工作区设置和管理权限。

**Project**

- 具体作品。
- 多个无限画布。
- 项目资产库。
- 项目提示词库。
- 生成任务和结果。
- 项目成员和权限。

普通用户不需要反复操作 Workspace。

单工作区时隐藏切换入口，后台自动使用已授权的工作区。

## 7. 项目首页

登录后主要看到：

- 项目卡片。
- 最近使用。
- 新建项目。
- 项目搜索。
- 必要的管理入口。

项目卡片应以封面、名称和最近更新为主要信息。

普通成员仅看到有权访问的项目。

管理员可以通过管理入口配置团队、工作流和计算资源。

## 8. 项目内多个无限画布

一个项目可以创建多张画布。

例如：

- 角色设计。
- 场景设计。
- 构图与首帧。
- 视频生成。
- 素材探索。

画布独立保存布局与版本。

同一项目所有画布共享项目资产库、提示词库和授权媒体。

打开项目默认恢复上一次使用的画布。

没有画布时直接提供新建入口。

不能重新增加“创作首页 → 画布”的强制中转页面。

# 第四部分：正式 UI/UX 设计要求

## 9. 设计系统

继续使用当前新分支建立的 Design Tokens 与基础组件。

首先完善：

- 颜色。
- 字体和行高。
- 间距。
- 控件高度。
- 卡片尺寸。
- 弹窗。
- Popover。
- 下拉菜单。
- 工具提示。
- 加载状态。
- 空状态。
- 错误状态。
- 焦点状态。
- 深浅主题。

不要每开发一个页面就增加另一套独立的 CSS 规则体系。

可以采用成熟的无障碍组件基础，但不要再引入两套平行组件库。

## 10. 无限画布设计

无限画布是整个产品最重要的页面。

视觉优先级：

**媒体内容 > 当前生成操作 > 创作工具 > 管理信息。**

需要重点优化：

- 默认视口。
- 多画布切换。
- 节点卡片。
- 画布工具轨。
- 素材缩略图。
- 输入输出端口。
- 连线。
- 选中态。
- 节点快捷菜单。
- 节点组合。
- 工作流生成面板。
- 候选视频预览。
- 缩放和适应内容。

正式节点不能只是带图标的技术表单。

图片节点应以图片为主体。

视频节点应以视频封面、播放和时长为主体。

提示词节点应能清楚阅读、编辑和复制内容。

工作流节点应让用户直接理解其输入、参数和输出。

## 11. 画布交互要求

用户应能：

1. 从本地拖入图片、视频、音频。
2. 粘贴剪贴板图片。
3. 从项目资产库拖入素材。
4. 从提示词库插入提示词。
5. 新建生成节点。
6. 连接参考素材。
7. 选择工作流。
8. 填写参数。
9. 提交生成任务。
10. 在画布上查看结果。
11. 再用结果进行下一次创作。

不能把用户频繁导向多个独立弹窗。

对于简单操作，尽量使用就地浮层或轻量面板。

对于权限、版本恢复、危险操作等复杂内容，才使用必要的管理窗口。

## 12. 原型与生产界面必须统一

本次代码审查确认：

`apps/web/src/features/canvas/StudioCanvas.tsx` 是设计评审用画布。

正式业务画布目前仍然主要使用：

- `canvas/BoardWorkspace.tsx`
- `canvas/BoardSurface.tsx`
- `canvas/BoardExecutionPanel.tsx`

后续必须避免维护两套长期并行的正式画布。

请评估最佳的收敛方式：

- 保留现有正式 Board 数据合同和业务服务。
- 将原型中优秀的交互、组件与设计令牌迁入正式画布。
- 或将正式业务操作逐步抽离成可被新画布使用的控制层。
- 保证只有一套正式的画布交互基础。
- 设计评审入口可以暂时保留，但不允许成为替代真实生产页面的验收依据。

当前主应用将 `BoardWorkspace` 包装为全屏 Dialog。

请评估是否将其调整为正常的项目主视图或路由。

目标是降低弹窗依赖，简化导航与焦点管理，但不能在改动过程中破坏已保存的 Board 或任务恢复。

## 13. 新分支不要再重写一次

新分支已经完成项目卡片、主题、基础画布及生成面板的重建。

这些代码应当继续评估和复用。

不要因为这份指令又创建第三套 UI。

真正需要的是：

**设计统一 → 正式交互收敛 → 工程职责整理 → 业务缺口补齐 → 验收。**

# 第五部分：资产系统

## 14. 资产库是核心业务能力

每个项目有自己的资产库。

资产类型包括：

- 角色。
- 场景。
- 道具和产品。
- 风格。
- 图片。
- 视频。
- 音色。
- 旁白录音。
- 音效。
- 背景音乐。

不要为每类媒体重新实现一套文件上传及存储系统。

继续复用现有 AssetEntity、MediaAsset、MediaVersion 和 Storage。

## 15. 角色资产

角色需要支持：

- 名称。
- 描述。
- 主参考图。
- 多张形象参考。
- 可选正面、侧面、背面图。
- 不同造型和服装版本。
- 可选音色身份。
- 可选音频样本。
- 当前采用版本。
- 历史版本。

角色节点可以输出多种内容。

例如：

- 主形象 IMAGE。
- 参考图集合 IMAGE[]。
- 角色描述 TEXT。
- 声音样本 AUDIO。

但真实音频样本和音色元数据必须区别对待。

## 16. 场景资产

支持：

- 场景名称。
- 描述。
- 主参考图。
- 多机位参考。
- 光照与风格变体。
- 关联道具。
- 图片版本。

场景可以在多个画布引用。

## 17. 角色三视图

三视图是一个重要的高价值工作流模板。

但不是 Pullet Studio 内置的固定推理算法。

应通过可配置的图像生成工作流实现。

当前本地主要使用 MiniMax H3，不能假设 H3 的视频工作流可以直接生成高质量静态三视图。

如果尚无可用的生图工作流，先允许导入外部角色图片并建立资产。

角色多视图生成在配置并验证可运行模型后开放。

# 第六部分：项目资产权限

## 18. 默认项目私有

每份资产必须具有明确归属项目。

默认只有源项目中具有相应权限的成员可以查看和使用。

同一工作区的其他项目不能自动读取私有资产。

## 19. 指定项目共享

资产所有者或具备管理权限的成员可以授权指定项目使用资产。

共享引用应具有明确的版本和权限。

不要直接复制原始媒体作为共享的默认行为。

2026-11-07 用户确认增加工作区公共库与项目独立素材库。公共库的主动收录和「添加到项目」采用独立归档规则：收录只保存固定媒体引用；显式添加后形成目标项目自己的素材版本，并保留来源，后续公共条目移除不影响已导入版本。首包复用现有上传与存储链路生成独立项目文件，见[公共媒体库合同](modules/WORKSPACE-MEDIA-LIBRARY.md)。这不替代本节指定项目或用户的可撤销授权，未主动收录的源项目资源继续私有。

## 20. 指定用户共享

允许将某个资产授权给指定用户。

用户不能因获得单个资产授权而自动获得源项目其他内容的读取权限。

## 21. 权限边界

至少区分：

- 查看。
- 使用。
- 导出。
- 管理。

共享授权应具备撤销能力。

权限检查必须落实在服务端：

- 资产查询。
- 预览。
- 下载。
- 画布引用。
- 生成输入。
- 导出。

绝不能只隐藏前端按钮。

撤销共享后，不得再启动未经授权的新任务；历史已归档结果按明确归属与审计规则处理。

本功能涉及新的数据库和 API 能力，应作为独立业务工作包，不要与纯 UI 重构混成一个不可回滚的大提交。

# 第七部分：提示词库

## 22. 继续完善已有 Prompt Library

当前提示词库已经存在，不需要重新开发。

要求支持：

- 保存提示词。
- 搜索。
- 标签。
- 一键复制。
- 插入画布。
- 应用到生成节点。
- 修订历史。
- 正向与负向提示词。
- 工作流推荐。
- 可选模型标签。

用户可以使用 ChatGPT、Codex 或其他 Agent 在外部生成内容。

Pullet Studio 只负责管理和使用这些文本。

## 23. 模型专用提示词模板

参考 DX OS 中的 MiniMax H3 提示词编写 Skill。

可逐步支持：

- T2VA。
- I2VA。
- FL2VA。
- L2VA。
- Ref2VA。

不同模式可以拥有不同的提示词结构。

但不要求 Pullet Studio 自动编剧或自动生成所有提示词。

外部 Agent 可以按照模型规范生成提示词，用户直接复制到项目库使用。

生成时固定实际提交的完整提示词快照。

# 第八部分：ComfyUI 工作流与多参考输入

## 24. 工作流采用单 API JSON 导入

用户通过 ComfyUI 导出 API Workflow JSON。

Pullet Studio 工作流中心负责：

1. 读取 JSON。
2. 验证格式。
3. 显示节点依赖图。
4. 识别可配置输入。
5. 由管理员确认字段。
6. 绑定实际输出。
7. 保存 Workflow Profile 与不可变版本。
8. 测试后供创作者使用。

普通用户不需要操作原始 ComfyUI 节点。

## 25. 扩展 Workflow Profile 的正式能力合同

DX OS 的逆向资料中有一个特别值得借鉴的设计：

一个工作流不仅保存原始图，还包括：

- fields。
- outputs。
- capabilities。
- 输入用途。
- 媒体槽位。
- 可选与必需输入。
- 缺失输入处理方式。
- 工作流运行快照。

我们建议将这些思想融入已有 Workflow Profile，而不是创建第二套工作流系统。

具体建议：

每个公开输入字段至少能够表达：

- 稳定字段 ID。
- 显示名称。
- 实际数据类型。
- 对应 ComfyUI nodeId。
- 对应 input 名称。
- 输入用途 role。
- 参考媒体槽位和顺序。
- 是否必填。
- 默认值及校验规则。

输出能够表达：

- 媒体类型。
- 对应的工作流输出节点。
- 主要/预览/中间结果角色。
- 单项或多项输出。

能力能够表达：

- 文生图。
- 图生图。
- 图片编辑。
- 图生视频。
- 首尾帧视频。
- 多参考视频。
- 视频参考。
- 音频参考。
- 音频合成。

能力声明必须来自工作流配置及验证结果，不能只靠工作流名称猜测。

## 26. 多模态参考输入

这是后续核心业务缺口。

正式画布需要支持：

- TEXT。
- IMAGE。
- IMAGE[]。
- VIDEO。
- VIDEO[]。
- AUDIO。
- AUDIO[]。
- NUMBER。
- BOOLEAN。
- ENUM。

用户可以通过两种方式绑定：

**方式一：画布连线。**

例如：

角色 A 图片 → Reference Image 1。

角色 B 图片 → Reference Image 2。

场景图片 → Reference Image 3。

提示词 → Prompt。

**方式二：直接从资产库选择。**

不需要把每张素材都显示成一个独立节点。

两种方式应使用同一套输入合同。

必须支持参考素材排序、替换、移除、预览和固定版本。

## 27. 区分普通连线和生成依赖

现有画布已经支持注释连线与具名输入绑定。

必须继续保持这个区别。

普通连接不触发模型执行。

真正的输入绑定需要经过类型、数量、权限和工作流能力验证。

不允许因输入超出工作流能力而静默忽略素材。

## 28. MiniMax H3

当前优先使用已经配置的本地 MiniMax H3。

DXOS-Portable 中保存的 H3 Workflow Profile 包含：

- 5 个图片参考槽。
- 3 个视频参考槽。
- 3 个音频参考槽。
- 提示词。
- 比例、时长、分辨率与 Seed 等参数。

这是该 DX OS 工作流预设的实际字段数量，不代表所有 H3 工作流都只能使用这些数量。

Pullet Studio 需要根据**当前导入的具体 JSON**确定能力边界。

现有 I2V 与多参考 Ref2VA 必须区别对待。

只有真实 R2V 工作流的模型、节点及依赖准备齐全后，才能声明多参考生成已经可用。

不要修改用户当前已稳定运行的 ComfyUI 环境，不自动下载大型权重，也不要为了接口演示消耗真实 GPU。

# 第九部分：Generation 与结果管理

## 29. Generation 体系保持不变

继续复用现有：

- Generation Job。
- Worker。
- 任务持久化。
- 自动和手动实例调度。
- 工作流固定版本。
- 输入参数快照。
- 失败与恢复。
- 生成结果归档。

不得创建第二套生成执行系统。

## 30. 输入、结果与历史必须分离

参考 DX OS 的数据模型思想：

**Inputs：本次明确选择的输入素材。**

**Result：最新一次生成结果。**

**History：历史生成候选。**

最新生成结果不能自动加入输入素材集合。

如果用户希望将结果作为新的参考，必须通过明确的“继续生成”“作为参考图”等操作完成。

这样可以防止输入条件悄悄变化，导致模型重复迭代失控。

## 31. 结果必须可复用

生成完成后：

- 在画布显示结果。
- 支持图片/视频预览。
- 支持继续生成。
- 支持加入项目资产库。
- 支持放入同项目其他画布。
- 支持下载原件。
- 保留任务、输入、工作流和版本关系。

浏览器关闭不应停止 Worker。

刷新页面后不能出现重复任务或丢失结果。

## 32. 媒体引用

参考 DX OS 统一文件节点的设计原则：

**资产和媒体以稳定 ID 引用，业务对象不直接依赖裸文件路径。**

Pullet Studio 已有 MediaVersion 和 Storage，因此应复用现有能力。

不要再造一套 DX OS 的虚拟文件系统。

注意：

- 删除画布节点不代表删除原始媒体。
- 同一媒体可被多个画布引用。
- 资产撤权后应控制新访问。
- 文件回收与永久删除应考虑有效引用。
- 缩略图与原件权限一致。
- 跨项目共享不等于自动公开媒体 URL。
